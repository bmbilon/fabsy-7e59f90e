**Original proposed server event contract — outside the later browser/privacy patch**

The business source of truth is one validated, paid checkout, recorded once independently of website navigation. Customer acquisition means new paying clients; order count is not automatically new-client count, particularly for separately purchased reports/add-ons.

| Order classification | Existing Stripe `fabsy_product` | Undiscounted service revenue, CAD | Purchase items |
| --- | --- | ---: | --- |
| RR | `rapid_resolution` | 198 | RR × 1 |
| RR bundle | `rapid_resolution_bundle` | 229 | RR at 198 × 1; report add-on at 31 × 1 |
| Standalone IDR | `insurance_impact_review` | 49 | Report × 1 |
| Later IDR add-on | `insurance_impact_review_addon` | 31 | Report add-on × 1; separate from original RR purchase |

These are catalog reference amounts, not hardcoded reporting values. Report the actual paid service amount after promotions/credits, in `CAD`, with GST in `tax` and the full charged amount retained separately for reconciliation. Google specifies that GA4 purchase `value` excludes tax and shipping and equals the item price/quantity total. See [Google's purchase event reference](https://developers.google.com/analytics/devguides/collection/protocol/ga4/reference/events#purchase).

| Event | Trigger and safe payload | Role |
| --- | --- | --- |
| `view_item` | Public offer view; offer/product variant, sanitized public landing path | Secondary funnel metric |
| `ticket_upload_completed` | Successful private file upload confirmed by the application; no filename or document contents | Secondary funnel metric; do not call this a completed free review |
| `intake_completed` | Server accepts the required intake and authorization; use an opaque event reference, not ticket/case details | Secondary funnel metric |
| `begin_checkout` | Server successfully creates/reuses the intended Stripe checkout; product, currency, expected service value | Secondary funnel metric |
| Internal `paid_order` → GA4 `purchase` / selected Google conversion / eligible Meta `Purchase` | Verified paid webhook plus matching reservation; stable transaction/event reference, payment timestamp, product/items, actual service revenue, tax, currency, environment, approved attribution and consent snapshot | Authoritative purchase; only the chosen RR/RR-bundle conversion action should be primary for RR campaigns |
| Internal refund/adjustment | Verified refund/adjustment linked to the original payment; own idempotency key and actual amount | Revenue and CAC reconciliation; implement before using net-revenue scale rules |

Use a stable opaque transaction reference mapped internally to the Checkout Session, never a timestamp, email, ticket number, or access token. Persist destination delivery state with a unique key on checkout/session + event kind + destination. Retry failed destinations without creating a second order. If a browser purchase remains, share the same canonical transaction reference; if Meta browser and server events are later permitted, share their canonical event reference and verify deduplication in its test tools. Do not count both a GA4-imported purchase and a second direct Google purchase action as separate primary goals.

The GA4 transaction ID observed in the August 30 checkout was already stable; a page refresh is not proof that GA4 counts an extra purchase. Google documents transaction-ID deduplication for web purchases. The unconditional `generate_lead` observed then had no equivalent application guard; it is not part of the published receipt path, whose later consent-gated activation is recorded above. See [Google's transaction-ID guidance](https://support.google.com/analytics/answer/12313109?hl=en).

For a GA4 server route, persist the actual permitted browser `client_id` and session context; UTMs alone are not a substitute for that linkage. Keep its API secret server-side. Google describes the required web-stream identifiers in [Measurement Protocol sending guidance](https://developers.google.com/analytics/devguides/collection/protocol/ga4/sending-events). Choose between the verified GA4-import path and a direct Google paid-conversion integration using current account capabilities before implementing both.
